Hosting de planes generados por IA

El plan del agente vive en el browser. Tu feedback vuelve solo.

Borrador es un servicio chico donde un agente de IA publica su plan como HTML, vos lo leés con formato, dejás comentarios anclados a partes concretas, y con un botón le decís al agente si lo refina o lo implementa. Todo por turnos: el agente publica, vos comentás, el agente responde con una versión nueva.

Cómo funciona Ver la API
Qué es

Cuatro cosas, tres contenedores

Planes con versiones

Proyectos con planes adentro. Cada publicación del agente es una versión nueva en la misma URL; las anteriores se guardan con sus comentarios. El HTML vive en Postgres, no en disco.

Comentarios anclados

Hacés click en un párrafo, una tabla, un título, y escribís. El comentario queda pegado a ese elemento con un selector CSS. El agente recibe selector + texto, no "el tercer punto de riesgos".

Por turnos

Solo comentás cuando es tu turno. El agente solo publica cuando es el suyo. Nadie pisa a nadie, y no hay condiciones de carrera que explicar.

Dos botones

Refinar pide una versión nueva. Implementar aprueba el plan y el agente pasa a ejecutarlo. El servidor solo registra la acción; el agente la viene a buscar.

Stack

Elysia + SvelteKit + PostgreSQL

Dos servicios y una base, como pide la guía: el frontend se encuentra con el backend por nombre a través de nginx, y el pipeline construye dos imágenes. Una sola API JSON bajo /api: el browser la usa con cookie, el agente con API key. Tipos de punta a punta con Eden, sin generar nada.

FE

SvelteKit, SPA

adapter-static servido por nginx, que proxea /api al backend. En dev, el proxy de Vite hace lo mismo. Cookie same-origin, sin CORS.

BE

Elysia sobre Bun

Rutas con validación integrada que delegan en services/. Drizzle para schema y migraciones. Better Auth con Google. Se testea en proceso con app.handle(request).

DB

Postgres

Único estado del sistema. Usuarios, proyectos, planes, versiones, comentarios, acciones. Migraciones al arrancar.

Cómo funciona

Un servidor, dos clientes

La instancia de Claude Code no es un servidor. Es un cliente, igual que el browser. La única conexión "rara" es un long-poll: una request que el agente deja abierta hasta que haya una acción pendiente. Como siempre la inicia el agente, no hace falta que tu laptop tenga un puerto abierto, ni túneles, ni webhooks.

01

El estado es la conversación

No hay un proceso "pausado". El transcript de la sesión guarda todo; la CLI espera. Si la cerrás, claude --resume la trae de vuelta.

02

Un script en background

El agente lanza el long-poll en background con run_in_background. Cuando termina con el JSON, el harness reinvoca al modelo. Sin que escribas nada.

03

Se despierta por botón, no por comentario

Los comentarios se acumulan en silencio. El botón es el "enviar". Así el agente no regenera el plan a mitad de tu revisión.

Turnos

Estados del plan

POST plan (v1) ──▶ turno_usuario ── refinar ──▶ turno_agente ── resolver (v n+1) ──▶ turno_usuario
turno_usuario ── implementar ──▶ aprobado ── resolver (v final, opcional) ──▶ aprobado

Comentar y accionar solo en turno_usuario. Una sola acción pendiente por plan; la segunda recibe 409. resolver es una transacción: crea la versión, consume la acción y marca atendidos los comentarios de la versión comentada.

Los dos botones

Así se ve el pie del visor

Refinar

"Todavía no. Tomá estos comentarios y dame otra versión." El plan pasa a turno_agente. El agente publica la versión nueva resolviendo la acción, y te vuelve el turno. Podés repetir las veces que quieras.

Implementar

"Está bien, con estos últimos cambios." El plan queda aprobado en el momento del click. El agente recibe los comentarios finales, publica una versión final si cambió algo, y arranca a implementar. Es tu aprobación humana, con fecha, en la BD.

API

Lo que habla el agente

Todo bajo /api. El browser manda la cookie; el agente, Authorization: Bearer <api key>. Las dos resuelven al mismo usuario. Lo que sigue es la parte que usa el agente.

POST /api/proyectos                     { nombre }            find-or-create
POST /api/proyectos/{id}/planes         { titulo, contenidoHtml, sessionId? }
                                        → 201 { id, url, version: 1 }
GET  /api/planes/{id}                   estado · versionActual · agenteEscuchando
GET  /api/planes/{id}/versiones/{n}/contenido   text/html

GET  /api/planes/{id}/acciones/siguiente?wait=25
       → 200 { accionId, tipo, plan: { id, titulo, version },
               comentarios: [{ id, selector?, texto }], contenidoUrl }
       → 204  venció el timeout, volvé a pedir

POST /api/acciones/{id}/resolver        { contenidoHtml? }    → 200 { version }
GET  /health

El ciclo del agente, en prosa

  1. Genera el HTML del plan. HTML plano, sin nada especial.
  2. Crea el proyecto por nombre (o lo obtiene) y publica el plan. Guarda el id, le da la URL al usuario.
  3. Lanza el long-poll en background. Termina el turno.
  4. Se despierta con la acción. Si es refinar: edita el HTML, resuelve la acción con la versión nueva, vuelve al paso 3.
  5. Si es implementar: incorpora los comentarios, resuelve (con versión final o sin ella), y sigue con la tarea original.
📘 Nota · el payload del long-poll trae contenidoUrl y no el HTML: si el agente perdió contexto, lo baja; si no, ya lo tiene. El anclaje de comentarios lo inyecta el visor dentro del iframe vía srcdoc; el HTML del agente no incluye ningún script.
Cuenta y token

Google para vos, una API key para tus agentes

Login con Google

Better Auth, OAuth server-side, cookie HttpOnly, sesión en la BD. Es el mismo flujo de siempre y la interfaz nunca toca un token.

Una API key por usuario

Se genera en la pantalla "Token", se muestra una sola vez, se guarda su hash. Regenerar invalida la anterior. Quien la tenga publica y resuelve como vos: riesgo asumido y documentado.

Compartir un plan

Toggle viewAccess por plan: owner (por defecto) o everyone (cualquiera con el link lo ve, sin cuenta). Comentar y accionar sigue siendo del dueño.

Decisiones

Lo que ya se cerró, y lo que queda abierto

✅ Atomicidad. Publicar la versión y consumir la acción van juntas en resolver, una transacción. No hay estado a medias.
✅ Selectores frágiles. Un comentario pertenece a una versión y no necesita sobrevivir a la siguiente. La fragilidad deja de importar.
✅ Comentarios a destiempo. Solo se comenta en turno_usuario. El agente nunca recibe la mitad de una revisión.
✅ Long-poll y proxies. wait default 25 s, máximo 55 s. Sobrevive a cualquier proxy que aparezca en TP6/TP7 sin configurarlo.
✅ Dos servicios, no un monolito. Se consultó a la cátedra: un solo módulo se acepta pero se desaconseja, porque el TP2 evalúa cómo se encuentran dos contenedores y cómo un pipeline construye dos artefactos. Backend y frontend separados desde el inicio.
⚠️ HTML no confiable. El visor usa iframe sandbox sin allow-same-origin y una CSP. Es el tema de seguridad real del TP9.
💡 Revivir sesiones. Si la CLI del agente se cerró, nadie la despierta. Fuera de alcance; se guarda sessionId por si algún día se hace.
Para el TP

Por qué esta app y no otra

✅ Frontend + backend + base, en tres contenedores. nginx con la SPA, Elysia en Bun, Postgres. Se levanta con docker compose up; dos Dockerfiles multi-stage y un nginx.conf con el proxy, como pide la guía.
✅ Tamaño justo. Seis tablas, cuatro pantallas: proyectos, planes, visor, token. CRUD más un long-poll. Nada más.
💡 Reglas para testear (TP5). Ownership propio/ajeno, nombre único, comentar y accionar solo en turno, segunda acción → 409, dos transiciones, resolver transaccional. Ocho reglas reales para el backend, probadas en proceso contra Postgres; cuatro comportamientos de UI para el front.
📘 Aprobación humana nativa. "Implementar" es una aprobación con fecha en la BD. El TP6 pide despliegues con aprobaciones; la app ya trae el concepto.
💡 Se entiende entera. Es propia, chica, y la única pieza no trivial (el long-poll) cabe en un párrafo. Eso importa para los cambios en vivo del Integrador.
⚠️ Una dependencia externa. Google OAuth. Gratis y estable, y ningún test pasa por ahí.
Fuera de alcance

Lo que deliberadamente no tiene

  • Roles, equipos, múltiples API keys.
  • Comentarios o acciones de quien no sea el dueño.
  • Diff entre versiones. Solo se listan y se abren.
  • Flechas, dibujos, resaltados libres.
  • Webhooks, SSE, notificaciones.
  • Revivir sesiones de agente cerradas.
  • Archivos fuera de la BD (S3, disco).
  • Más de una instancia del servidor.
  • La skill y el script del agente dentro de este repo.
  • SSR en el frontend. Es una SPA estática.
